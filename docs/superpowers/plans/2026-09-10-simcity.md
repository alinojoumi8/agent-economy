# Agent Economy City Integration Plan

> Implementation workflow: use superpowers:executing-plans to implement the unchecked tasks in order. This document plans the integration; it does not claim that the game client or new economic mechanics exist.

**Goal:** Turn Agent Economy into an explorable, SimCity-inspired city where buildings, citizens, firms, and institutions expose the actual economy and its evidence.

**Architecture:** Keep Python as the authoritative simulation. Author original modular assets in Blender, export GLB, and add an optional 3D city view to the existing React dashboard. Read versioned, authorized projections; submit economic proposals only through existing validated engine paths.

**Tech stack:** Existing Python/FastAPI/SQLite and React/TypeScript/Vite; Blender 5.2.1 verified locally. Proposed renderer: Three.js, with a dependency/version/license check during implementation.

**Spec:** The product and architecture sections below define the proposed design. `DESIGN.md`, `AGENTS.md`, and `docs/development.md` remain applicable except for the explicitly requested isometric city direction on this branch.

## Product direction

The primary loop is **observe → inspect → propose → advance → explain**. Zoom from districts to a citizen or firm, inspect its jobs and transactions, follow a permit or business formation, advance the engine, then see what changed and why. Player powers are explicit: an observer can inspect authorized information, a participant can act as their controlled agent, and an operator can use authorized run/scenario controls. A camera gesture never confers government authority.

Use an orthographic, low-poly city with readable silhouettes and a restrained civic palette. Residential blocks are low rise; business districts are taller; public institutions are distinctive. The existing evidence lens remains live HTML alongside the canvas. Keep colors and labels grounded: selection cobalt, communications cyan, verified settlement chartreuse, rejection vermilion. Building finishes are material choices, not undocumented heatmaps.

The user explicitly requested a SimCity-like direction. On this branch, an isometric city is intentional despite the current `DESIGN.md` prohibition. Preserve its stronger rules: provenance, keyboard access, reduced motion, and inspectable evidence. Before shipping the viewer, add a documented optional City 3D exception to that file. Build original assets and interface; do not import SimCity branding or game assets.

### Options considered

| Approach | Benefits | Costs | Decision |
|---|---|---|---|
| Blender assets + browser 3D in existing dashboard | Reuses identity, run selection, evidence, controls and deployment | WebGL budget and accessibility work | Recommended first release |
| Blender assets + standalone Godot client | Strong terrain, pathfinding and game tooling | Another application, protocol, packaging and UI to maintain | Reconsider after playable mechanics prove demand |
| Blender-only animation or rendered sprite atlas | Simple asset/render pipeline and attractive stills | Cannot itself provide a responsive evidence-linked simulation interface | Use for concept and low-end fallback research |

Blender is the authoring tool, not a second simulation engine. First deliver a truthful observer city. Introduce construction/zoning only after the observation slice passes, since these affect accounting and replay.

## City-to-economy mapping

| City feature | Authoritative source | Visual treatment and boundary |
|---|---|---|
| Citizen | Authorized agent + presence projection | Selectable marker at known place; derived placement visibly labeled if absent |
| Home / workplace | Existing place, lease and firm relationships | Stable asset instance linked to place/firm; no invented home ownership |
| Office / workshop | Organization and place kind | Silhouette from explicit type; unknown industry gets neutral building |
| Bank | Authorized bank/institution view | Inspector; no inferred reserves or private balance sheet |
| Civic hall | Licensing office, agency, service cases | Queue count only when projection authorizes it; no hidden attendees exposed |
| Work / appointment | Tick-and-slot effective presence | Movement interpolation is illustrative, not evidence of actual road travel |
| Settlement | Committed event/transaction | Evidence-linked pulse; balances only from authoritative projections |
| Failed business / rejected permit | Explicit lifecycle or rejection event | Named state and evidence; do not infer failure from missing data |
| Roads, parks, river | Visual layout, currently synthetic | Decorative until separate mechanics are implemented and versioned |

## Contracts and invariants

1. **One authority:** all mutation stays in `engine/` or deterministic `world/`; every monetary effect uses balanced ledger legs. Renderer state is disposable.
2. **Stable identity:** key instances by `(run_id, fork_id, entity_type, entity_id)`. Never use array order or a display name as identity. Concept IDs in the Blender manifest are not production entity IDs.
3. **One coherent view:** preserve the existing envelope; add `city_layout_version` only in the proposed adapter output. Cache by complete lineage, tick, projection/policy versions and view key. Clear on run, fork or principal changes. Never combine live presence with historical buildings.
4. **Historical honesty:** audit historical coverage field by field. If a requested field cannot be reconstructed, omit it or label it unavailable; never fill it with the current value. Inspect `map_places` and service queue calculations before claiming historical fidelity.
5. **Deterministic placement:** use source coordinates when available; otherwise a versioned stable hash of entity identity and region assigns a derived slot. Avoid Python process hash and never consume the engine PRNG. Preserve existing placements as new entities arrive; resolve collisions in sorted ID order or a persistent layout sidecar. Record transform, seed and layout version.
6. **Coordinate contract:** source coordinate bounds must be verified. Transform them into a documented region-local grid. Blender uses Z-up; GLB export converts to glTF Y-up. Consume the exported convention once, not an extra hand-coded axis swap.
7. **Visual clock:** interpolate only between known snapshots and stop on pause/stale data. Label travel as illustrative. Reduced-motion mode uses discrete updates. Provider activity remains ephemeral telemetry, never settlement evidence.
8. **Synchronization:** initially retain existing scoped polling. Use WebSocket notifications as invalidation hints only after inspecting their current payload contract. A cursor gap or reconnect triggers a fresh authorized snapshot. Do not assume the current socket offers ordered deltas.
9. **Privacy:** use existing principal-aware routes. Do not embed private balances, conversations, run databases or agent context in GLB/custom properties or a public export. Asset extras contain asset metadata only.
10. **Compatibility:** read-only visualization needs no engine semantics bump. New zoning/construction/transport effects require the next appropriate semantics gate discovered at implementation time; preserve exact v1/v2 replay and never alter a stored source run.

Proposed pure client interface in `dashboard/src/city/cityProjection.ts`:

```ts
type CityInstance = {
  key: string;
  entityType: 'agent' | 'firm' | 'place' | 'institution';
  entityId: number;
  assetKey: string;
  position: [number, number, number]; // renderer coordinates
  provenance: 'observed' | 'derived';
  evidenceIds: string[]; // only references supplied by authorized projections
};
// Concrete input types must match existing projection contracts.
// projectCity(envelope, layoutConfig) => { envelopeIdentity, instances, warnings }
```

Use source labels as text nodes. Unknown asset keys use a neutral placeholder. A malformed/unsupported envelope yields an explicit error, not a new synthetic city mislabeled live.

## Implementation sequence

### Phase 1 — Modular asset kit (small independent deliverable)

**Files:** extend `city/blender/build_city.py`; add `city/blender/export_assets.py`, `city/assets/catalog.json`, `city/validate_assets.py`; generated production assets eventually enter `dashboard/public/city/`.

- [ ] Split concept buildings into reusable collections with ground-centered origins, unit dimensions, stable asset keys, and low/high detail variants. Parent windows and roof parts with their building; the current scene is a composed concept, not yet an instancing kit.
- [ ] Export one GLB per asset family with plain supported materials and metadata; avoid baked labels and external textures. Pin Blender version and record source/export hashes in catalog.
- [ ] Validate unique keys, dimensions, axes, missing references, finite transforms, triangle/material counts, and successful GLB reimport. Reject duplicate catalog IDs and oversized assets.
- [ ] Render contact sheet and inspect each silhouette at city zoom and close zoom. Test one house, office, bank and civic hall in the target browser before expanding the kit.

**Acceptance:** reproducible catalog; no missing materials; all pivots sit on ground; compressed delivery target <=10 MB for first-view kit. These are proposed budgets, not measured current performance.

### Phase 2 — Read-only city projection (first integration boundary)

**Files:** create `dashboard/src/city/cityProjection.ts` and a pure testable layout module following current dashboard test conventions; add `dashboard/tests/city-projection.test.js`. Extend `server/projections/workspaces.py` and `server/v2_api.py` only if existing responses lack necessary authorized fields; add `tests/test_city_projection.py` if backend changes.

- [ ] Capture sanitized provider-free legacy and civic envelopes in test fixtures. Enumerate actual place kinds and coverage by tick.
- [ ] Write tests for stable mapping, order independence, collisions, unknown kinds, empty city, closed places, absent coordinates and invalid envelopes.
- [ ] Implement `projectCity` as a pure function; reuse existing envelope/view scope. Document source units and deterministic fallback.
- [ ] Test run/fork/principal isolation, historical truth and unavailable fields. Confirm no engine writes by comparing source artifact hashes before/after projection reads.
- [ ] Verify counts against source records: each visible place/firm mapped once; hidden entities absent; every rendered evidence reference resolves under the same principal.

**Acceptance:** same snapshot + layout version gives the same instances; zero mutations; no private data leakage or live/historical mixing.

### Phase 3 — Interactive dashboard city (first usable release)

**Files:** create `dashboard/src/city/CityViewport.tsx`, `CityScene.ts`, `assetLoader.ts`; modify `dashboard/src/workspaces/OverviewWorkspace.tsx`, `dashboard/package.json` and lockfile; add `dashboard/tests/city-viewport.spec.ts` using repository Playwright configuration/conventions; update `DESIGN.md` and generated `server/static/` bundle.

- [ ] Pin and license-check a compatible Three.js release. Mount it behind a 2D/3D toggle, initially defaulting to the existing view.
- [ ] Add orthographic pan, bounded zoom, rotation presets, reset camera, district layer visibility, and selection. Keep inspector and controls as HTML.
- [ ] Bind raycast results to stable entity keys and reuse existing selection/evidence URLs. Keyboard users can select from a synchronized entity list without a canvas.
- [ ] Add loading, empty, stale, unsupported-WebGL and asset-load error states. Offer existing atlas fallback; dispose GPU resources on unmount and view change.
- [ ] Verify pause/step and historical navigation, resize/mobile layout, reduced motion, keyboard focus, direct links and disconnected backend behavior.
- [ ] Test repeated mount/unmount and 30-minute operation for growing GPU/heap usage. Use shared geometry/instancing before considering richer detail.

**Acceptance:** clicking a workplace opens its real evidence; pausing stops state progression; camera changes leave ledger/state untouched. Initial targets: >=30 FPS at 1080p for 300 agents + 100 places on an explicitly recorded integrated-GPU machine; first usable view <3 s on local network. Report hardware and measured results; tune or reduce visual detail if missed.

### Phase 4 — Evidence-linked economic activity

**Files:** create `dashboard/src/city/cityActivity.ts`; extend `CityScene.ts` and focused tests. Use `server/projections/events.py` and existing event inspection rather than a parallel event store.

- [ ] Map supported committed event kinds to brief named effects with evidence links; reject unknown or unauthorized payloads safely.
- [ ] Show employment, civic appointment and settlement activity only where source fields support it. No synthetic monetary values or animated invented trades.
- [ ] Deduplicate by event identity, cap visible effects, cancel on lineage change and suppress current runtime overlays in history.
- [ ] Test duplicate notifications, out-of-order arrival, cursor gaps, reconnect, large event bursts and exact historical event selection.

**Acceptance:** every economic animation can explain its source; no animation creates economic state; absence of evidence produces no invented event.

### Phase 5 — Playable civic decisions, then construction

Split this into two separately reviewed changes. First expose already-supported participant permit/appointment actions with current authorization and rejection reasons. A rejected request must leave city state and money unchanged; successful requests wait for authoritative settlement before changing visuals.

Only then design new construction/zoning mechanics. Candidate files: new `engine/urban_development.py`, additive schema in `engine/schema.py` using the repository migration contract, typed actions through `engine/actions.py`, deterministic phase hooks in `world/loop.py`, and `tests/test_urban_development.py`. Verify existing land/place ownership support before defining new tables; do not duplicate leases or permits.

- [ ] Specify actor authority, land rights, zoning, build cost in cents, capacity, completion tick, cancellation/refund rules and insufficient-funds rejection.
- [ ] Add success, rejection, replay, reconciliation and concurrent/double-submit cases before integrating the UI.
- [ ] Charge through ledger escrow/settlement, use idempotent action identity, persist build lifecycle events, and gate new behavior by the appropriate new semantics version.
- [ ] Add build placement previews that are explicitly proposals; commit geometry only after engine acceptance. Server validates placement/cost; client cannot choose authoritative prices.
- [ ] Exercise closures, demolition, actor death, blocked parcels and run resume with funds reconciled at each boundary.

**Acceptance:** a participant can follow a real permit and eventually propose a funded building whose completion is deterministic and replayable. Old runs remain exact. Traffic, electricity, water, pollution and disasters are later economic features requiring their own specifications; they are not hidden within this viewer project.

## Verification and release

For the concept: run Blender headlessly, reopen the `.blend`, reimport the `.glb`, check manifest/building identity and finite bounds, and inspect the PNG. Record actual verification in `city/README.md`.

For integration: run the focused suite below after backend changes, plus new projection/city tests. For dashboard changes run `npm --prefix dashboard test`, `npm --prefix dashboard run typecheck`, `npm --prefix dashboard run licenses:check`, relevant Playwright tests, and `npm --prefix dashboard run build`. Review/commit the generated bundle. Before release run the full gate in `docs/development.md`, including cross-platform, replay, dependency and secret checks; a concept smoke run is not that release gate.

```bash
python -m pytest -q tests/test_documentation.py tests/test_external_agent_gateway.py tests/test_research_export.py tests/test_prd_completion.py tests/test_recorded_replay_golden.py
```

Recommended review units: (1) concept and plan, (2) modular kit, (3) pure projection adapter, (4) selectable 3D viewer, (5) economic events, (6) civic controls, (7) newly versioned construction. Each unit has its own acceptance gate. Do not ship future phases merely because their visuals exist.
