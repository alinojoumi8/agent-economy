# 5. Framework Decision — Adopt vs Build

Chapter 4 specified the POLIS target architecture — an event-sourced kernel, actor-per-agent concurrency, deterministic institutional reducers, and a Cognition Scheduler — without justifying why none of it rests on an existing framework. This chapter is the justification trail, written as a decision record (options → criteria → decision → consequences). The method had three stages: a census of candidates across three framework families — classic agent-based modeling (ABM) frameworks, LLM-agent societies, and general-purpose agent runtimes — with licenses verified against repository LICENSE files; elimination on hard constraints; and weighted scoring of the survivors. One contextual fact shapes everything that follows: at 10⁴–10⁵ LLM agents, the framework's own stepping loop is a rounding error in the runtime budget — AgentSociety measured environment simulation and message-passing times "far below LLM inference time" while running 30,000 agents faster than wall clock on 24 A800 GPUs [^46^]. The selection question is therefore not "which framework steps the most agents per second" but "which substrate provides asynchronous LLM orchestration, persistent world state, deterministic replay, and cost control inside a Python/TypeScript product stack." *Citation note: `[^N^]` indices follow the source research reports per section — §5.1.1: Dim01; §5.1.2: Dim02 with Dim01 supplements; §5.1.3: Dim05; §5.2–5.3: Dim01/Dim02.*

## 5.1 The Candidates Evaluated

### 5.1.1 Classic ABM frameworks

**Mesa (Python, Apache-2.0 [^4^])** is the strongest classic candidate and the only one with an official LLM story. Mesa 3.x is the current stable line (3.2.0 shipped April 2025); activation runs through the AgentSet API, and the Mesa 4.0 alpha promotes discrete-event scheduling to a first-class module (`mesa.time`) [^1^][^5^]. Its community is the largest in Python ABM (140+ contributors, 500+ citing papers) [^1^]. Three findings disqualify it as the production base. First, scale: the project's own mesa-frames extension concedes that classic Mesa's per-agent Python objects "quickly become a bottleneck at scale," places the practical ceiling near 10³ agents, and reaches ~10⁶ only through columnar, vectorized updates that explicitly exclude "strict per-agent sequencing, complex non-vectorizable methods, or fine-grained identity tracking" — a precise description of an LLM-agent economy [^6^]. Second, throughput: in the continuously maintained cross-framework benchmark suite, Mesa 3.2 runs 3.3×–9.4× slower than Agents.jl on WolfSheep and 27×–159× slower on Flocking/Schelling [^22^]; Mesa is single-threaded under the global interpreter lock (GIL), with multiprocessing batch runs as the standard mitigation [^14^]. Third, LLM support is immature: Mesa-LLM (GSoC 2025) plugs OpenAI/Anthropic/xAI/Ollama-class providers into Mesa agents but self-declares pre-release — "the API and functionality may change significantly" [^8^] — and the community's 2026 roadmap discussion lists larger scale and LLM-driven agents as open questions, not shipped features [^7^]. Verdict: an attractive prototyping bench, disqualified as the 10k–100k engine.

**Agents.jl (Julia, MIT [^18^])** is the performance leader: the fastest CPU framework in the maintained benchmark suite, a stabilized continuous-time `EventQueueABM` since v6.2, and struct-of-arrays agent storage in v7 [^16^][^22^]. It fails on stack and ecosystem rather than capability: POLIS is a Python/TypeScript build, and the Julia LLM-agent ecosystem is effectively absent — no sanctioned integration exists, only generic packages such as PromptingTools.jl [^15^]. The Mango.jl authors abandoned Python over asyncio and the lack of native multithreading [^25^], but the concurrency POLIS needs is LLM-I/O fan-out, not CPU multithreading — and Julia supplies no LLM layer either. Verdict: retained only as an option for closed-form, compute-bound sub-models callable via JuliaCall/PythonCall; rejected as the base.

**MASON, Repast, NetLogo — rejected.** MASON sustains ~10⁶ agents headless but is explicitly single-process (distribution exists only as research variants), carries an unusual Academic Free License 3.0, is Java (off-stack), and has no LLM story [^31^][^32^][^33^]. Repast Simphony is mature but Java/Eclipse-centric with a slow cadence (~one release per 1–2 years; v2.11.0, July 2024); its sibling Repast4Py (BSD-3, MPI-distributed Python) targets CPU-bound rule-based workloads on HPC clusters — heavy machinery mismatched to an LLM-latency-bound product [^27^][^28^]. NetLogo 7 is GPL v2-or-later with a models library mostly under CC BY-NC-SA (non-commercial) — a licensing trap for a commercial world-sim — and is positioned even by its own community as a prototyping tool for small models, measured 4–10× slower than Agents.jl in a 2025 head-to-head [^37^][^24^][^1^].

### 5.1.2 LLM-agent societies

The second family is younger and directly on-domain. The decisive cross-verified observation: **none of these systems is built on a classic ABM framework, and none is a general-purpose engine POLIS could adopt** — each is a bespoke kernel aimed at a specific research scenario (cross-verification, Tier-1 finding #1).

**Concordia (Google DeepMind, Apache-2.0 [^43^])** is the closest thing to an adoptable harness. Agents are entities composed of modular components mediating two primitives — LLM calls and associative memory retrieval — while a tabletop-RPG-style Game Master (GM) owns the world, checks physical plausibility, and translates natural-language intents into outcomes, including API calls into simulated digital apps such as email, calendar, and search [^27^]. It ships a unified `LanguageModel` interface with retry, call-limit, and profiling wrappers [^42^], is actively maintained on PyPI as `gdm-concordia`, and its 2025 successor paper claims reach "to a complex economic simulation with thousands of agents and external events" [^29^]. It remains turn-centric and research-grade, with no built-in million-agent scaling path [^8^] — the right pattern source, not the right kernel.

**OASIS (CAMEL-AI, Apache-2.0 [^51^])** demonstrates million-agent scheduling through five modular components — Environment Server, Recommendation System, Agent Module, Time Engine, and Scalable Inferencer — with an hourly activity-probability clock that wakes only a fraction of agents each step, asynchronous channels between modules, and a GPU request broker [^49^][^50^]. Its scientific finding that herd effects emerge reliably only above ~10,000 agents fixes POLIS's minimum population target [^52^]. Its social-media specificity (feed actions, text-only, no purchasing) means the engine does not transfer wholesale.

**AgentSociety (Tsinghua FIB-Lab, Apache-2.0 [^48^])** is the reference runtime recipe: Ray distributes agents across process groups, asyncio hides LLM latency, and MQTT pub/sub sustains ~44,702 messages per second [^47^]; 30,000 agents ran faster than wall clock with an average 252-second agent round and near-linear scaling in GPU count [^44^][^46^]. Its mind model (Maslow needs, emotion state, Theory-of-Planned-Behavior cognition) and its urban-economic scenarios are on-domain, but the engine ships no ledger, courts, or elections.

Around these three: **Generative Agents** (Stanford) remains the cognitive reference architecture — memory stream, reflection, planning — at 25 agents and thousands of dollars per two-day run at 2023 prices [^355^][^369^], and its 1,000-person successor used a custom `genagents` codebase rather than any framework [^57^]. **AI Town** (a16z×Convex, MIT [^149^]) proves the event-journal web architecture on a single shared async runtime, at tens-of-agents demo scale [^142^]. **EconAgent** put ~100 LLM agents on Salesforce's custom Foundation engine for 240 simulated months [^55^]. **Project Sid** released no code [^364^]; MetaGPT (MIT [^218^]) contributes the role/SOP organization pattern for institutions, not a world.

### 5.1.3 Agent runtimes and harnesses

The third family orchestrates LLM work but does not simulate worlds. **LangGraph** provides durable execution, checkpointers, and human-in-the-loop for one agent's cognitive graph — it has no per-entity actor concept and no simulation clock; state is graph-run-centric [^48^][^42^]. **AutoGen and CrewAI** optimize conversational and role-based task teams, and practitioners report a "complexity wall" when such prototypes reach production [^49^][^50^]; AgentScope (Apache-2.0 [^222^]) contributes actor-based distribution and fault-tolerance ideas worth studying. **SimPy and salabim** are the correct mental model — priority event queues, resources, monitors — but the wrong runtime: single-threaded synchronous generator processes with no LLM-native batching [^2^][^3^]. **Temporal-style durable execution** journals every workflow step so a crashed worker resumes at the exact failed step — the right discipline for multi-tick sagas (lawsuits, funding rounds), not for the world loop [^46^]. Finally, the actor substrates: Orleans supports millions of virtual actors, but its own documentation disqualifies it where global coordination is needed — and market clearing, elections, and courts are global coordinators [^41^]; Akka cluster sharding proves the JVM equivalent for thousands-to-millions of entities [^44^]; and **Ray actors are the Python-native choice** [^45^], already proven at 30,000 LLM agents by AgentSociety (§5.1.2).

The table exposes a structural gap that no single candidate crosses. Proven scale and native LLM support appear together only in the bespoke societies (Concordia, OASIS, AgentSociety), and those fail domain fit — none ships a double-entry ledger, market clearing, courts, or elections. The classic frameworks invert the problem: mature scheduling and visualization, but no LLM layer and ceilings three orders of magnitude below target. The runtimes split the difference and solve neither side: LangGraph/AutoGen/CrewAI manage conversations, not simulated time; SimPy manages simulated time, not LLM I/O. Licensing, often the hidden veto in framework selection, eliminates only the already-weak here — NetLogo's GPL-plus-non-commercial model library and MASON's AFL-3.0 oddity [^37^][^31^]; every serious contender is permissively licensed, so the decision turns on architecture, not legal risk.

## 5.2 Decision Matrix

### 5.2.1 Weighted criteria and scoring

Six criteria survived the elimination round; their weights are a **design decision** fixed by the build context — a solo-builder Python/TypeScript product targeting 10k–100k agents with a hard replay requirement: scale ceiling and concurrency model (0.20); determinism, replay, and audit support (0.20); domain fit to ledgers, markets, courts, and elections (0.20); LLM-cost controls, meaning async batching, activation sampling, and provider abstraction (0.15); team stack fit (0.15); license and governance (0.10). Determinism and domain fit carry the top weights because they are the two properties POLIS cannot retrofit: replay must be designed into the state model from the first commit, and no framework plugin supplies a stock-flow-consistent economy. Scores run 1–5 against the documented evidence of §5.1, on a reproducible rubric: 5 = proven at or above the requirement; 3 = partial, needs adaptation; 1 = absent. "Custom kernel" is scored on the architecture specified in Chapter 4, borrowing the patterns marked in Table 5.1.

| Criterion (weight) | Mesa 3/4 + Mesa-LLM | Agents.jl 6/7 | Concordia (adopt as base) | OASIS / AgentSociety (adopt as base) | LangGraph / AutoGen / CrewAI | Custom kernel + borrowed patterns |
|---|---|---|---|---|---|---|
| Scale ceiling & concurrency (0.20) | 2 | 5 | 2 | 4 | 2 | 4 |

Three properties of the result matter more than the totals. First, the margin is structural, not tunable: every adoptable candidate scores 3 or lower on both top-weighted criteria, so no re-weighting that keeps determinism and domain fit at or above 0.15 each changes the ranking — the gap between the custom kernel (4.80) and the best adopt option (3.30) exceeds one full point even if license weight is zeroed and stack fit doubled. Second, Agents.jl (3.00) scoring above Mesa (2.95) despite losing stack fit confirms that raw throughput was never the deciding variable; a framework five times faster changes nothing when the bottleneck is LLM inference [^46^]. Third, the strongest adoptable option, OASIS/AgentSociety (3.30), earns its score almost entirely through proven scheduling and cost controls — which is precisely why those patterns, rather than those codebases, enter the build in §5.3. The matrix also records that Concordia (3.15) is the only candidate whose domain-fit score reflects a transferable mechanism (Game-Master adjudication for litigation, founding, and negotiation) rather than a missing subsystem [^27^][^29^].

## 5.3 Verdict

### 5.3.1 Build a thin kernel; borrow proven patterns

**Decision.** POLIS builds a custom thin simulation kernel in Python — Ray actor-per-agent, asyncio fan-out, a Postgres event store, and a Redis/MQTT-class message bus — and borrows four validated patterns from the societies that already solved their slices of the problem. This is not a not-invented-here preference; it is the convergent outcome of every comparable project. Concordia, AgentSociety, OASIS, SocioVerse, Project Sid, EconAgent, and both Stanford generative-agents codebases were all custom kernels [^41^][^44^][^49^][^57^], and the high-confidence cross-verification across three independent research dimensions records that no existing ABM framework or agent runtime is a drop-in base (Tier-1 finding #1). Teams with far larger engineering budgets than POLIS evaluated the same candidate set and unanimously chose to build thin and borrow.

**What POLIS builds** is deliberately irreducible: the logical-time event queue with barriered tick batches; the append-only event log with snapshots and the decision journal; deterministic reducers for institutions; the activation sampler; and the Cognition Scheduler. The kernel owns time, state, causality, and cost — nothing else.

**What POLIS borrows**, with provenance:

- **Game-Master adjudication and component architecture** (Concordia, Apache-2.0): entity/component agents, GM resolution of open-ended natural-language actions, and the `LanguageModel` wrapper discipline of retries, call limits, and profiling [^41^][^42^] — code-level reuse is license-permitted wherever the turn engine does not bottleneck.
- **Activation sampling** (OASIS): the hourly activity-probability time engine and GPU request broker, which make million-agent scheduling tractable by waking only a fraction of agents per step [^49^][^50^].
- **The runtime recipe and scaling calibration** (AgentSociety): Ray process groups + asyncio + MQTT at ~44.7k messages/s, with the 252-second, 30,000-agent round as POLIS's public calibration point [^47^][^44^].
- **Cognition and evaluation references**: the Generative-Agents memory stream (recency × importance × relevance, reflection, planning) as the agent cognition baseline [^355^]; LangGraph-style checkpointed graphs *inside* an agent's decision pipeline, never as the world runtime (§5.1.3); Temporal-style journaled sagas for multi-tick processes such as lawsuits and funding rounds (§5.1.3); and a Sotopia-style multi-dimensional, LLM-judged evaluation harness (MIT [^147^]) for agent social quality.

**Consequences.** On the positive side, POLIS owns the event schema and the scheduler — the two surfaces on which replay, the cost-per-sim-day SLO, and every downstream UI view depend — and the kernel stays small because institutions are deterministic reducers and cognition is a stateless decision service (Ch. 4). The accepted costs are explicit: POLIS forgoes Mesa's visualization and community tooling (mitigated by the bespoke TypeScript front end specified in Ch. 10) and assumes kernel-maintenance burden a framework would amortize (mitigated by the kernel's thinness and golden-run replay tests gating every change). Two monitoring triggers could reopen this decision: Mesa-LLM reaching a stable 1.0 [^8^], or Concordia shipping a scalable asynchronous engine [^29^]. For build order the verdict is unambiguous: **the kernel is built first.** Milestone M0 is the event-sourced kernel plus the stock-flow-consistent ledger, running 200 rule-driven agents behind a golden-run replay gate, because the economy engine of Chapter 6, the cognition services, and every institution reducer are producers and projections over that log; no adopted framework could have supplied it.
